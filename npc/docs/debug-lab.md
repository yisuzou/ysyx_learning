## 第一题：看起来大多数访存都正常

复现：`python3 npc/tests/debug_lab.py case1`。

场景：在合法 RAM 地址读取固定数据，分别使用不同宽度和符号扩展方式。普通 word、unsigned halfword、signed byte 及部分 signed halfword 对照组均可工作，但后续边界输入出错。

已观察现象：原始数据包含 `0x8001`，一次读取的预期结果是 `0xffff8001`，实际得到 `0x00008001`。原始数据由 TB 明确提供，不依赖内存初始化或 C 编译器。

你需要回答：

1. 地址、总线返回值、最终 CPU 响应，哪一处最早偏离预期？
2. 为什么同一个原始数据可能因访问方式不同而得到不同的正确结果？
3. 哪些输入会隐藏这个 BUG，哪些最容易暴露它？
4. 如何区分“选错字节/半字”和“扩展错误”？

验收：既有 case1 全部通过；自己补充一个正数边界、一个负数边界，说明为什么它们不是重复测试同一种情况。保持 byte/halfword/word 和 signed/unsigned 对照组。

## 第二题：外部结果正确，但交出去的结果不对

复现：`python3 npc/tests/debug_lab.py case2`。

场景：向执行阶段提供一条 load 任务。访存请求经历背压后被接收，访存服务再延迟数拍提供正确结果。测试分别让最终结果接收方立即可用、暂时不可用。响应生产者在握手后按协议改变自己的输出数据。

已观察现象：立即接收的对照组返回 `0x11223344`；阻塞场景应得到 `0x89abcdef`，却得到零。请求地址和任务身份也有检查。

你需要回答：

1. 从访存响应到最终结果交付，经过了几次不同的握手？
2. 响应握手的那个沿之后，谁有责任保存数据？
3. 上游在握手后改变数据是否违反接口契约？
4. 最终接收方暂时不可用，允许影响哪些行为，不允许影响哪些行为？

验收：立即接收与背压两组都通过；自己改变响应到达时间、最终接收方停顿长度，检查每条任务恰好一次请求、一次响应、一次结果交付，所有等待期间 payload 稳定。

注意：本题是独立接口测试。当前单指令全核中，最终接收方经常恰好空闲，因此完整程序可能无法触发这个错误。测试人为制造的是协议允许的等待，不是错误的总线行为。

## 第三题：结果收到过，但指令没有完成

复现：`python3 npc/tests/debug_lab.py case3`。

场景：先提供一条最终结果并正常提交，作为对照组；然后提供第二条结果，让下一 PC 接收方暂时不接收，再恢复接收。测试同时监测待提交身份、架构 PC、写使能与提交次数。

已观察现象：第二条结果最初已被接收，但等待期间“待处理指令”消失，无法满足后续提交要求。

你需要回答：

1. “接收到执行结果”“提供下一 PC”“交付下一 PC”“提交指令”分别是哪一个事件？
2. 暂停期间哪些状态应保持，哪些副作用必须禁止？
3. 消息的提供是否等同于对方已接收？波形中有什么证据？
4. 恢复接收后，如何证明是恰好提交一次，而不是零次或重复提交？

验收：立即接收与暂停接收均通过；自己增加更长等待，并补测合法 EBREAK 与非法指令，确保它们的特殊终止语义没有被修复破坏。

同样，这是独立接口测试。即使当前 IFU 在健康单指令执行中通常已经 ready，WBU 的接口实现也应正确处理合法背压。不要通过把测试中的 ready 永远拉高修复它。
